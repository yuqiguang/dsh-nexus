# 编码任务的检查与恢复

任务执行、独立检查与人工验收分别记录。默认全部约定检查和交付文件核验通过、当前版本任务及依赖均结束且通过后可以交付；主助手仍须核对完整用户要求。人工验收仅在用户明确要求时询问。编码工具返回成功、某个工具退出 0 或文件已经展示，不能替代这些检查。

## 登记逐项检查

`coder_task.verify_commands` 是完整检查列表，每条直接启动实际程序，按顺序执行；失败后保留该项失败，并把后续命令记为未执行。不要用 `pwsh -Command`、`bash -c` 或 `cmd /c` 拼接检查并打印子进程退出码。需要包装脚本时，脚本本身必须检查失败并返回非零退出码。

多项验收用 `acceptance_checks` 明确关联，命令必须同时列在 `verify_commands` 中。`files` 相对任务 `cwd`，与 `verify_cwd` 无关。例如：

```json
{
  "description": "按说明单完成项目并准备检查入口",
  "brief_id": "当前说明单 ID",
  "brief_revision": 1,
  "acceptance_ids": ["a1", "a2"],
  "verify_commands": [
    "python checks/check_output.py",
    "python checks/check_docs.py",
    "python checks/reproduce.py changed-input"
  ],
  "outputs": ["result.zip", "README.md", "status.json"],
  "acceptance_checks": [
    {"criterion": "a1", "commands": ["python checks/check_output.py"], "files": ["result.zip"]},
    {"criterion": "a2", "commands": ["python checks/check_docs.py", "python checks/reproduce.py changed-input"], "files": ["README.md", "status.json"]}
  ]
}
```

检查脚本应覆盖约定的实际行为：文档是否更新、报告引用的交付文件是否生成、修改输入后的分支是否真正运行等。Nexus 不从业务关键词生成断言；只做语法检查不能证明这些要求已满足。

`outputs` 和 `files` 会检查普通文件、真实路径与内容摘要。文件存在不证明内容正确；内容语义由对应命令检查。交付汇总及用户验收时重新核对这些文件的摘要，检测到验证后的变化会显示需复验，不改写原任务。未声明的文件仍可能出现在改动审计中，但不会据此自动算作交付物或发送到渠道。

单验收项任务可以沿用它已登记的完整检查列表。多验收项没有明确对应关系时，任务级检查结果仍保留，各项显示证据未齐；旧记录不会补造已执行检查。某项通过不会覆盖另一项的失败或未执行，整体交付还须满足任务验证；明确要求的人工验收与已有未满足反馈也会影响交付状态。

步骤计划也支持 `acceptance_checks`、`outputs`。计划的 `verify` 为第一条命令，`verify_commands` 为追加命令；任务工具的 `verify_commands` 则为完整列表。续接可以增加检查，但不能丢弃同版本已有命令、文件和验收项；修改要求应先变更说明单版本。

## 按需确认实际结果

`coder_brief delivery` 只汇总证据，不弹出问题。默认 `require_user_review` 为 false，缺少人工回答不会阻止检查通过的任务交付，也不会被记录成用户已认可结果。只有用户明确要求人工验收作为交付条件时，在 `save` 设为 true；更新说明单时省略会保留原设置，计划与续接也会保留。

仅说明单要求人工验收，或用户主动要求确认结果且 `review` 带 `user_requested: true` 时才提问。不要从“界面”“业务效果”或“测试通过”等字样自行开启。问题包含目标、验收项、查看方法、结果摘要和已核验文件，并说明三个选项：

- 已满足：用户已查看结果，符合该项要求。
- 未满足：结果仍有问题，可补充具体原因；当前证据下继续阻止交付通过。
- 暂时无法判断：尚未查看或不知道如何核对，保留待确认；不记为接受或拒绝。

同一版本、同一结果的回答持久保存，默认不重复提问，包括暂时无法判断。用户明确要求重新确认时，同时传 `user_requested: true` 与 `reconfirm: true`。重新回答无法判断会撤回同证据的已满足结论，但保留尚未解决的未满足反馈。文件、任务或目标版本变化后按新证据核对；验收期间发生变化会拒绝记录旧回答。尚未结束的任务不会发起人工验收。

## 沿原任务恢复

先读取 `coder_brief` 的 `recover`。没有步骤计划时，恢复清单同样会提供最新任务的续接参数。已有后续执行的旧任务不能再次恢复。

- 编码中断：用户明确继续后，用最新任务的 `retry_task_id` 或 `resume_task_id` 核对已有文件并完成剩余工作。有原生编码会话时沿原会话续接。
- 编码已结束、验证失败或条件需修正：指定最新任务并设置 `verification_only: true`，只运行宿主检查。中断编码不符合这一条件。
- 交付：读取 `coder_brief delivery`，补齐各项检查与声明文件，处理已有未满足反馈；只有用户明确要求时调用 `review`。主会话临时检查不会替代原恢复链中的独立验证。

原任务状态及审批历史保留。原生用户回答只授权当次请求，并关联任务、目录、会话和目标版本；曾批准探针不代表批准后续扩大范围的执行。

## 过程交互与会话核验（0.2.71）

Codex 运行中的普通补充使用 `coder_steer`。当结构化 `needs_input` 已结束当前回合、正在等待用户回答时，非中断补充按顺序暂存，真正回答后一起进入同一线程的下一回合；取消后不再启动下一回合，补充不会传给后续问题。运行中原生提问或审批仍由原请求等待回答。此状态下 `interrupt: true` 不会替用户回答已结束回合的问题。

Claude 的手动与自动续接均核对 `session_id`；工具返回替换会话时停止，不把新会话当作原上下文。Gemini 续接要求 ACP `loadSession` 能力、完整原生会话 ID 和同一项目；使用 `session/load`，不会失败后悄悄改用 `session/new`。关闭任务后先清理原进程与工具桥，再进行自动续接。

查看已保存的过程记录直接使用会话存储目录，不检查当前工具是否仍安装、登录或支持新任务权限；更改设置不会让原任务的过程记录消失。实际续接仍须通过安装、凭据与原权限检查。

Gemini 的 `nexus_coder` 工具提供 `read_file`、`write_file`、`replace_text`、`command`、`ask_question` 和 `report_result`。提问交给 DSH 原生问题服务及原任务用户，必须得到真实回答；最终报告必须是最后一个工具调用，状态为 `completed`、`needs_input` 或 `blocked`，或在最终消息提供同形的严格 JSON。普通结束回合不自动证明任务完成，报告后有新工具操作或工具失败需重新报告。宿主独立验证继续执行。

Gemini 推荐版本为 `@google/gemini-cli` 0.71.1。本版仅启用 Nexus 私有工具桥，配置及原生会话存储与项目配置隔离。支持标准与完全权限；严格沙箱拒绝派发，运行中插话需先取消再续接。单次文件读写最多 1 MiB、前台命令最多 120 秒，不支持交互式 stdin 或跨调用后台服务；命令退出及取消时回收子进程，模型凭据不传给命令子环境。

## 重试与显示

工具内部重试和 Nexus 自动续接分别计数。两者共享本次任务的无进展等待计时：自最后一次成功操作起，累计重试等待 5 分钟提醒、10 分钟暂停。审核或用户等待不占此计时；普通状态消息不会把计时清零，成功工具操作会重置它。原有总运行预算和自动续接上限（网络或服务故障两次、限流四次）继续生效，重启不重放任务或审批。

Gemini 的原生 `_meta.retry` 记录显示工具内部重试，重试后的消息重置不拼接旧回答。ACP 的 HTTP 错误码用于区分限流、认证与永久拒绝；负数 JSON-RPC 协议错误不当作服务故障。成功读写及命令计入实际进展。Google OAuth 刷新只写回合法对象，并保留并发任务或新登录已经更新的凭据。

改动摘要优先展示明确声明的文件、代码和报告；`pydeps`、虚拟环境、包目录与已知缓存分组。编号图片仍保留在项目文件和完整审计中，目录外改动检查不因显示分组而省略。

上述机制使用本地模型与文件样例做回归。Gemini 另用未修改的官方 CLI 0.71.1 与本地假模型响应验证 ACP、私有 MCP 文件与命令操作、原生提问、同一会话加载及 JSONL 记录；未使用真实模型账号或发送渠道消息。本地通过不代表真实外部服务、Google 浏览器登录或 Windows 桌面发布验收。
